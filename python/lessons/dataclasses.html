ООП 5. Dataclasses

Избавляемся от рутины (без нейросетей)

У нас новое задание. Теперь надо создать приложение для школьной столовой, а значит, что нужен класс, который хранит информацию о каждом блюде: название, калорийность, цена. До этого момента мы писали бы какой-то такой код:

Код ещё почти ничего полезного не делает, а буковок уже получилось многовато, не правда ли?

А что, если для нашего приложения надо написать не один десяток таких классов? Каждый раз нас будет ждать примерно одно и то же, только имена полей будут меняться.

К счастью, эра самописных конструкторов подходит к концу. В Python 3.7 появился декоратор @dataclass, про который мы сегодня и поговорим.

Необходимость в чём-то похожем на @dataclass созрела уже довольно давно, да и в других языках программирования идея автоматической генерации шаблонного кода (его ещё называют boilerplate) уже была хотя бы частично решена — в Java есть Lombok, в Kotlin — data classes, в Scala — case classes.

Программисты в Python долго смотрели на это богатство и шли на разные ухищрения, используя:

namedtuple — удобно, но это кортеж, а значит, неизменяемый;

attr — хорошая библиотека, но надо устанавливать отдельно;

просто словари — тоже, в общем, рабочий способ, но IDE не подсказывает нормально ключи.

🤐 Без лишних слов

Хватит ходить вокруг да около, давайте писать (а точнее, давайте не писать лишний) код. Для начала импортируем нужный декоратор:

Вот так теперь будет выглядеть наш класс для блюда в столовой:

@dataclass

КОД — ВСË! Пять строчек, если считать декоратор, и у нас есть полноценный класс с:

автоматическим .__init__(), который всё бережно разложит по атрибутам класса;

красивым __repr__ для отладки;

работающим оператором равенства __eq__, который вернёт True для двух объектов класса Dish, если они имеют одинаковые значения для всех атрибутов, и False в противном случае.

Как это работает: когда Python видит декоратор @dataclass, он говорит: «О, тут аннотации типов! Сейчас я по ним создам все нужные методы». Он смотрит на name: str, calories: int и так далее, и автоматически генерирует код.

Это как если бы у нас был робот-помощник, который смотрит на чертёж дома и сам строит фундамент, стены и крышу. Но чертеж рисовать всё равно нужно.

💁 Общеизвестные факты

В мире не так много неизменных вещей, одна из них — писать меньше кода, сохраняя его функциональность. Например, не хочется указывать все параметры при создании объекта. Например, большинство котиков пушистые, так зачем каждый раз это писать?

@dataclass

Нужно помнить о том, что все поля без значения по умолчанию должны объявляться до полей с значением по умолчанию. Это правило похоже на параметры функций в Python: нельзя после параметра с дефолтом объявить параметр без дефолта. Если попробовать нарушить, получим ошибку:

@dataclass

При попытке запустить скрипт с таким классом Python вежливо ругнётся: TypeError: non-default argument 'b' follows default argument 'a'. Исправляется просто: b нужно объявить выше a, или дать b тоже какое-то значение по умолчанию.

Очень важное напоминание: нельзя использовать изменяемые объекты в качестве значений по умолчанию.

В этот раз Python более настойчив и даже не позволит нам выстрелить себе в ногу:

@dataclass

Если мы попробуем запустить этот код, Python выдаст:

ValueError: mutable default value: list is not allowed: use default_factory

🎓 Экспертный режим

Декоратор @dataclass умеет не только генерировать методы по умолчанию, но и позволяет настроить поведение класса под свои нужды. Для этого у декоратора есть несколько параметров. Перечислим главные из них:

repr — отвечает за автогенерацию метода .__repr__(). По умолчанию repr=True, и dataclass сделает красивое строковое представление объекта. Если поставить repr=False, метод .__repr__() не будет сгенерирован вовсе. Это может пригодиться, если вы хотите определить свой вручную или если отображать объект не имеет смысла.

eq — (внезапно) отвечает за метод равенства .__eq__(). По умолчанию eq=True, и объекты сравниваются по всем полям. eq=False отключает автогенерацию сравнения: тогда a == b будет True только если a is b. Отключать это имеет смысл редко, разве что ваш класс несравним по логике или вы хотите сами реализовать особое сравнение.

order — включает генерацию методов сравнения .__lt__(), .__le__(), .__gt__(), .__ge__(). По умолчанию order=False. Если включить, dataclass сгенерирует эти методы, сравнивая объекты лексикографически по всем полям в порядке их объявления. Важно: для order=True требуется, чтобы eq=True (иначе неясно, как сравнивать). Также все поля должны поддерживать сравнение, иначе при попытке сравнить объекты получите ошибку. Пример использования:

@dataclass(order=True)

frozen — делает ваши объекты неизменяемыми (иммутабельными) после создания. Если frozen=True, то любой попытке присвоить значение атрибуту экземпляра после инициализации бросится ошибка FrozenInstanceError. При frozen=True dataclass автоматически реализует метод .__hash__() (по умолчанию, если eq=True). Иначе говоря, «замороженные» экземпляры можно класть в set или использовать как ключи в dict.

unsafe_hash — если очень нужно, можно насильно включить метод .__hash__() даже для изменяемых dataclass. Но слово unsafe (небезопасный) прозрачно намекает: разработчик берёт на себя ответственность не менять объект, пока он используется как ключ в словаре, иначе словарь сломается. Честно говоря, лучше не включать этот флажок без крайней необходимости.

init — по умолчанию True, что заставляет @dataclass генерировать стандартный .__init__(). Обычно не отключают, разве что у вас специфический случай: например, вы хотите определить свой .__init__() вручную или использовать dataclass в качестве класса-наследника, где конструктор уже задан в родителе.

match_args — параметр, появившийся в Python 3.10. По умолчанию True. Он отвечает за интеграцию со структурным сопоставлением (match/case). Когда match_args=True, dataclass определяет специальный атрибут __match_args__, благодаря которому вы можете распаковывать объект в match как кортеж из полей. Например:

@dataclass

kw_only — ещё одно новшество Python 3.10. Если указать kw_only=True, то все поля dataclass станут именованными параметрами (keyword-only) в сгенерированном .__init__(). То есть при создании объекта придётся явно писать ClassName(field=value), передавая значения по имени. Это бывает полезно, когда у класса очень много полей и легко перепутать порядок аргументов или при наследовании (чтобы избежать проблем с порядком параметров).

slots — если указать slots=True, у сгенерированного класса будут определены __slots__ для полей. Это означает, что экземпляры класса не будут иметь обычный __dict__ (словарь атрибутов), а хранение данных станет более компактным и немного более быстрым. Минус — нельзя добавлять новые атрибуты динамически (да обычно это и не требуется). Этот параметр пригодится, если вы собираетесь создавать миллионы объектов и важна каждая капля памяти. Для обычных программ выигрыш от slots минимален, так что без крайней нужды можно о нём не беспокоиться.

Как видите, настроек много — на все случаи жизни. Чаще всего, конечно, достаточно стандартных, но приятно, что при необходимости можно одним аргументиком включить, например, полный порядок сравнения или сделать объекты неизменяемыми.

👻 Из ниоткуда

Можно пойти ещё дальше (и в некоторых случаях приходится) и обойтись вообще без объявления класса в исходном коде, создавая его динамически.

Это случай, когда нам захотелось сгенерировать класс на лету, например, в зависимости от входных данных. С dataclass такое возможно с помощью функции make_dataclass().

make_dataclass() — это фабричная функция, которая создаёт новый класс dataclass по заданному имени и списку полей. Проще всего показать на примере:

Функция make_dataclass() первым параметром принимает имя класса (строкой), вторым — список полей. Каждый элемент списка — это либо имя и тип поля, либо кортеж из имени, типа и дополнительной информации (например, field(default=...) или field(default_factory=...).

Дополнительно можно передать аргумент bases (кортеж базовых классов, если хотим, чтобы наш новый класс был наследником каких-то классов) и namespace — словарь с дополнительными атрибутами или методами класса.

Проще говоря, make_dataclass() делает то же самое, что и декоратор, но в программном стиле: вы описываете класс данными, а функция возвращает готовый класс-объект. Это довольно специфичная возможность: в учебных задачах вы вряд ли будете её использовать. Однако в продвинутом коде, где нужно генерировать структуры динамически (например, конструировать классы на основе входных JSON-схем или ещё каких-нибудь данных), такая магия может пригодиться.

🏆 Всё еще достоин

Использование dataclass вовсе не ограничивает нас в функциональности класса. Это всё тот же Python-класс, которому просто помогли с бытовухой. Можно спокойно добавлять собственные методы, свойства, классовые методы — всё, что душе угодно.

@dataclass

Стоит упомянуть особый метод .__post_init__(). Если его определить, он будет вызван автоматически сразу после сгенерированного .__init__(). Это полезно, когда нужно выполнить дополнительную инициализацию или проверку полей. Например:

@dataclass

Теперь при создании User("KittyKat«) в конструкторе сохранится «KittyKat», а затем .__post_init__() тут же преобразует username в «kittykat». Можно делать любые проверки и преобразования: например, убедиться, что возраст не отрицательный, обрезать пробелы в строках и т. д. Главное — помнить, что .__post_init__() получает уже полностью созданный объект, и в нём доступны все поля, включая те, что имеют значение по умолчанию, даже если их не передали в конструктор.

Ещё .__post_init__() часто используют в комбинации с полями, помеченными как init=False. Такие поля не попадают в конструктор, но их можно вычислить или установить как раз в .__post_init__(). Однако чтобы не погрязнуть в деталях, достаточно знать, что этот метод — наш помощник для любой дополнительной работы сразу после создания объекта.

⚜️ Дворянские корни

Dataclasses поддерживают наследование, и это работает почти так же, как с обычными классами. Почти. Есть пара нюансов, о которых нужно знать.

Сначала пример без подвоха:

@dataclass

@dataclass

Мы видим, что .__repr__() подтянул поля и из базового класса, и из наследника. Сравнение (.__eq__()) тоже будет учитывать все поля (Student сравнивается как Person + school).

Первый подвох. Помните правило про поля с дефолтами? Оно действует и при наследовании. Если в базовом классе есть поля с значениями по умолчанию, а в подклассе появляются новые поля без дефолтов, Python опять-таки бросит ошибку (нельзя же параметр без значения ставить после параметра с значением). В Python 3.10 эту проблему решили — можно объявить в базовом классе @dataclass(kw_only=True), тогда все его поля станут требоваться только по имени, а у наследника спокойно добавятся новые позиционные поля.

Ещё момент: если в базовом классе определён .__post_init__() для дополнительной инициализации, то в наследнике при переопределении не забудьте вызвать super().__post_init__(), чтобы базовый класс тоже выполнил свою работу. Это стандартная практика при наследовании — dataclass тут не исключение.

А как насчёт наследования от обычного (не dataclass) класса? Такое тоже возможно. В этом случае @dataclass сгенерирует .__init__() только для своих полей, а начальную инициализацию базового класса придётся вызывать самому. Обычно это делают либо вызовом super().__init__() в .__post_init__(), либо вообще отключают автогенерацию конструктора (init=False) и пишут .__init__() вручную. Но это уже экзотика. В подавляющем большинстве случаев вы будете наследовать один dataclass от другого, и это довольно удобно.

🌟 Итог: краткость — сестра таланта

Мы проделали немалый путь: от ручного создания классов к декоратору, который делает всё скучное за нас. @dataclass позволяет избавиться от шаблонного кода и сосредоточиться на самой сути — данных и логике работы с ними. Вместо того, чтобы раз за разом писать .__init__() или .__repr__(), мы пишем то, что реально важно для решения задачи.

Конечно, dataclass — не серебряная пуля. Но в контексте хранения данных и простых объектов он стал настоящим спасением от тонны повторяющегося кода. Сегодня это стандарт де-факто для Python-разработчиков, когда речь идёт о классах данных. Кроме того, модуль dataclasses предоставляет функции asdict() и astuple(), которые одним вызовом превращают dataclass-объект в словарь или кортеж.
